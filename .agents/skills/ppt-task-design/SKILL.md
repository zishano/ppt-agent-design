# Presentation task design

1. Read the original request, supplied materials and repository guidance. Inventory actual files before describing their contents. Record title, audience, intended decision, language, reading context, output types, data cutoff and source policy in brief.json.
2. Separate required wording from a proposed thesis. Extract user obligations into stable R IDs with source anchors and acceptance checks. Record exclusions and permissions to research or use illustrative data. Default to supplied-material-first; research only necessary gaps using permitted authoritative sources and record provenance.
3. Analyze reference images by canvas, hierarchy, grouping, chart types, source footers, typography roles and reading sequence. Record desired traits and nonrequirements. A screenshot is a visual reference, not a database; unreadable labels remain unknown.
4. Decide routine style, page count and module arrangement. Ask only when an unresolved issue changes a consequential obligation: factual versus simulated output, mandatory unsupported conclusion, restricted source access, incompatible format or legibility requirement. Continue independent work. Never ask the user to supply values that available permitted sources can establish.
5. Define testable requirements before making pages: for example R1 retains all supplied business scenarios; R2 every forecast is labeled; R3 every quantitative visual has units and a source; R4 text remains editable. Avoid vague acceptance such as “professional enough”.
6. Save brief.json and continue ppt-mapping. An unsupported headline must be framed as a question or hypothesis rather than declared proven. Do not reject a useful task merely because some evidence is missing.

## Diagram-rich implementation

Paths in this section are relative to the package root. Record diagram_detail_policy=diagram-rich and the required explanatory questions in the brief. Distinguish richer diagram content from extra quantitative data or ornament. Name the objects and internal stages the reader must understand; do not impose the discarded 60-character limit.
