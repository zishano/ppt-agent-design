# 可编辑机制图风格（mechanism-editable）

可独立选择的 PPT 绘制风格，适用于技术原理、网络通信、软硬件协同、数据搬运和设备工作过程。调用示例：“使用可编辑机制图风格，讲解……”。它是现有四阶段 skill 的风格配置，不是第五个阶段或新的后端，不要求多代理。

这是独立的原生可编辑风格，与 [机制插画风格](mechanism-illustrated.zh-CN.md) 并存，不修改、替代或废止后者。

当前实现参照本地 v7 / v8 可编辑版（演示项目独立交付，不作为此 skill 的必需依赖）。保留原生文字、分组设备部件和机制路径；材质表现仍可继续优化，不声称与完整生成式插画等同。可借鉴原机制插画的层次与解释力，但不得以它的精细程度要求反向放弃本风格的编辑性。

## 可编辑性硬性要求

- 默认 `render_mode: native-editable-illustration`。标题、标签、参数、数据块、队列、设备部件、路径、反馈与表格必须是可选择、可修改的原生 PowerPoint 对象。
- 设备用原生几何形状 / 自由曲线构建立体面、板卡、芯片和接口，并按设备或机制分组，支持整体移动及取消组合后修改部件。不得用一张整图、SVG图片、EMF图片或透明文字覆盖图片冒充全可编辑。
- 图像生成可用于风格草图与视觉参考；交付时需按语义重建原生图元，不把自动描摹成碎片视作可用编辑性。关键文本必须是真正文本框。
- 不为原生化把机制删成几个空框；保持整机与内部过程、数据、状态和局部展开。几何插画可比生成式图片的材质简洁，但必须如实说明视觉差异，不能声称像素级复刻。
- 除非用户明确要求图片型 PPT，否则整页/主机制栅格化是验收失败。真实照片等辅助图片可保留，但不能承担必须编辑的标签、参数或机制路径；列明其例外。
- 路径是否随设备移动自动重连需实际验证。静态分段连线不能宣称自动布线；告知移动设备后可能需调整端点。

## 1. 风格识别

**风格基准必须实际查看** [原版总览](../../output/datacenter-network/visual-v3/assets/01.jpg)、[设备剖面](../../output/datacenter-network/visual-v3/assets/02.jpg) 和 [拥塞回路](../../output/datacenter-network/visual-v3/assets/04.jpg)，不能只凭“立体设备”几个字重新解释。这些资源只作画风和层次参考，具体图中关系与标签仍须按新主题重新核实。

- **一体化构图**：设备剖面、芯片/板卡、内存区域、数据块、队列、反馈回路与就地标注共同组成主图。文字嵌入机制，不能把完整解释挪到图外的文字卡片里。
- **丰富的技术插画质感**：银灰机箱、绿色 PCB、内部模块、适度阴影和立体数据块；粗细有层次的路径、带色标题条和圆角区域。允许参考版的鲜明色彩与适度渐变，不强制改成极简扁平图。
- **主场景 + 局部状态展开**：主图建立全程路径；局部放大显示队列占用、授权内存、包头、发送节奏、丢包恢复或完成条件。每个细节直接解释技术机制。
- **不是本风格的替代品**：重复一张设备素材，加细线连到几个矩形，再在页底放三张文字卡片；设备只是贴图、关键机制全部留给文字；为编辑性把整幅插画退化成稀疏原生框图。若用户另行选择混合原生风格，可使用，但不能称为本风格默认。


- 白底或浅底、深色标题、银灰机箱和绿色电路板，辅以少量有语义的强调色。
- 设备采用静态三分之四视角 / 等轴测技术插画，适度表现机箱、板卡、接口和内部部件；细节须服务于技术说明，避免无关光效。
- 设备承载机制：读者能沿路径看到数据从哪里来、经过哪个部件、状态如何改变、反馈返回谁。立体感服务于部件归属与连接理解。
- 主图占据视觉中心；局部放大、剖面、短注释解释关键黑盒。细节丰富度来自工作过程和状态变化，不来自装饰、硬件堆叠或无来源参数。
- 静态呈现，不添加 GIF、视频、动态转场。“动画风格”在这里指插画造型。

## 2. 先决定要讲什么

每页先写一个读者问题，再写直接回答它、且证据支持的标题。例如“CPU 做准备，网卡搬数据”，优于单独写“RDMA 技术介绍”。缩写首次出现时就地说明，文字用于命名、解释动作和必要条件，不设机械字数上限。

若主题含多个易混淆的概念，第一页优先画体系、包含、依赖或替代关系；无需硬塞设备图。不要把网络体系、上层协议、特性和规范画成同级的四个产品。先说明“是什么、解决什么”，再进入封装和设备路径。

选择一个贯穿例子，例如同一块 KV Cache 在两台 GPU 服务器之间传输。固定对象身份、端点位置、观察视角、数据块颜色和基本拓扑；各页只突出当前机制的变化，其他对象弱化但保留。不把“复用插画”误当作同一真实硬件支持所有协议。

末页用关系图或对照表回答“它是什么、基于什么、解决什么问题”。已解释过的设备不必再次占据主体。上述结构按主题适用，不强制六页或固定章序。

## 3. 图形语法

| 元素 | 绘制规则 |
| --- | --- |
| 实体设备 | 统一视角、比例感和细节等级；接口与引线可辨认 |
| 数据路径 | 带方向的主线，沿具体部件或端点连接；必要时标数据块身份 |
| 控制 / 反馈 | 与数据线区分颜色或线型，注明触发原因、反馈内容、受控对象 |
| 归属 / 包含 | 用容器、嵌套、底板或边界，不用数据箭头表示“属于” |
| 局部放大 | 从主图对应对象引出；解释缓冲、内存区域、包头、队列或部件职责 |
| 状态变化 | 前后状态或编号序列；说明产生变化的事件，避免只画彩色箭头 |
| 文字 | 标题给答案，标签说明对象或动作，短注释保留适用条件，来源可追溯 |

颜色按语义固定，不因协议名称换页而改变。同一数据块始终同色；数据、反馈、CPU 控制可分别用紫、绿、灰，但配色只是默认，可整体替换。颜色不能作为唯一识别方式，必须有文字、形状或线型辅助。主路径、反馈线、放大引线分级，交叉不等于连接；明确交汇点，避免箭头悬空或落在错误部件。

信息密度允许较高，但每个细节应回答一个技术问题。先画总过程，再展开当前核心黑盒一层；若读者只能复述“网卡、交换机和彩色箭头”，必须回到语义映射修订。

## 4. 事实与实物边界

- 指定真实型号：先研究官网、手册、论文或可追溯技术资料，记录型号、数量、位置和连接证据，再画。漂亮的插画不能证明结构真实。
- 概念机制：在许可范围内使用通用设备示意，明确标为示意；块数、端口数、缓存格、路径长度不暗示实测容量、吞吐或具体产品。未获授权的不确定几何不能偷偷补全。
- 缺失的关键参数不得猜测；可标“未公开 / 未核实”，或改用不依赖该参数的机制图。模型生成的文字、芯片数量、线路和参数都需复核。
- 涉及机器 / 机柜组成时，叠加 [实体机器规则](../physical-machine.zh-CN.md)：同页左侧统一整机、右侧编号分层说明；此风格决定画风，实体机器规则决定装配与数量要求。
- 风格不改变 [分层机制图合同](../diagram-rich.zh-CN.md) 的证据与解释力要求。

## 5. 制作工作流

1. **任务设计**：在 brief.json 记录 `visual_style: mechanism-editable`，声明读者、关系先导是否必要、贯穿案例、阅读尺度、示意许可和编辑性要求。
2. **语义映射**：在 deck-map.json 为每页记录 `reader_question`、`answer_title`、`case_state`、`focus_change`、`device_roles`、`data_path`、`feedback_path`、`invariants`、`evidence_ids`；不适用项注明原因。先明确语义，再安排坐标。
3. **原生插画制作**：先做一张密集代表页，检查画风与编辑性。按语义重建原生立体面、板卡、队列、数据块和路径，配真正文本框；对设备与局部机制命名分组。若用生成图作草图，应将其作为参考而非交付主图。
4. **导出可编辑 PPT**：使用原生对象导出，不将已绘制对象拍平。PPT 原生部件与标签为规范源，PDF / PNG 仅用于预览。选择 python-pptx 或 ppt-master 后执行适用后端约束；后端不支持的编辑需求应明确解决，不能改成图片后宣称完成。
5. **一致性与封装**：用共同参考、场景约束和检查保持角色及状态身份，避免跨页结构漂移。按展示分辨率压缩静态图片、避免重复嵌入不必要的大图；记录文件大小，不为固定体积牺牲标签可读性。
6. **实际渲染与验收**：检查最终 PPTX 的逐页渲染，再修订。来源图或生成原图好看不代表导出正确。

示例 brief 片段（字段可按项目补充，不代表已有 schema 自动校验）：

```json
{
  "visual_style": "mechanism-editable",
  "relationship_first": true,
  "running_example": "同一块 KV Cache 从 GPU 服务器 A 到 B",
  "render_mode": "native-editable-illustration",
  "color_roles": {"data": "purple", "feedback": "green", "cpu_control": "gray"},
  "editability": "文字、部件、数据块、队列、路径与表格原生可编辑；设备分组可取消"
}
```

## 6. 验收清单

- 先检查原生编辑性与机制表达，再对照本风格当前 v7/v8 实现优化设备层次、材质和局部细节；不以整图栅格化换取外观。
- 主图是否直接画出队列、内存、状态或关键内部过程？局部展开是否与主场景相连？
- 递归检查分组内对象：关键文字为文本框，部件和路径为原生形状/连接线，不存在整页图片替代。统计图片例外和用途。
- 在临时副本实际修改标题、数据块颜色和设备位置，保存重开检查修改仍然存在；检查取消组合后的部件可访问。保留验证记录，不能仅凭文件扩展名宣布可编辑。
- 原生文本与最终PDF逐页比对，并检查箭头、中文、遮挡及状态转换；文本提取不代替视觉审查。


- 不看设备细节，能否先说清概念之间的关系及各自解决的问题？
- 每页标题是否直接回答问题？机制变化是否有触发、过程和结果？
- 跨页的案例、设备位置、对象身份、颜色语义是否一致？
- 能否沿数据路径和反馈路径分别复述？反馈是否返回正确控制对象？
- 实际机器与概念示意是否区分？参数、数量、几何与协议能力是否有证据或明确边界？
- 局部细节是否帮助理解主图？是否存在装饰性设备、无意义连线或段落塞框？
- 末页能否帮助读者独立复述差异，而不只回忆设备名称？
- 最终渲染是否出现重叠、断线、文字失真、符号错误？编辑性说明、静态媒体和体积是否核验？

以上为代理执行与审查合同，不是已实现的自动语义或审美评分器。
